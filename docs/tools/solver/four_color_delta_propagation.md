2026-10-27。接續[訊息分區](four_color_information_partition.md)的局部代價限制，
本輪直接優化傳播工作，保留原消元排程。新增 `propagation_method="delta"`，
需啟用共同接口交集；預設 `scan`保留舊流程供比較。

後續另試[完整接口支援流失](four_color_support_loss.md)的`support`模式：

## 四項改動

1. **只排程變動的接口對。** 保留因子到接口對的相依索引。新因子或revision改變
   時才加入待處理佇列；依舊列表的字典序處理。這一輪游標以前的配對延至下一輪，
   以保持舊傳播順序、原因追蹤與消元紀錄，不改先做哪項推理。
2. **只刪列時，重用已完成的共同支援。** 記錄上一份完整交集的支援列數。
   若只有一側改變，另一側不必重新建立共同投影交集；新支援未減少時，兩表均不用再篩選。
3. **整張表就是接口時，直接引用。** 當完整接口包含該表全部欄位，且欄位順序相同，
   投影是恆等操作；直接使用既有不可變完整表，不另建逐列分組索引。
   有私有欄位或欄位順序不同時，仍使用完整投影及完整原列。
4. **先查局部條件，再建立全圖快照。** 共同環查詢先檢查環與共同點的候選域。
   局部簽章未變就跳過；只有需要查詢時才建立整張原圖的候選色mask。
   同一輪較早查詢縮域後，後面相交查詢仍讀最新域，不使用過時快照。

目前仍保留一般域傳播的掃描與既有快取、有界環發現、共同條件查詢以及最後精確消元。
不是所有傳播都改成區域佇列，也沒有宣稱局部傳播已完備。

## 為何支援重用精確

上次完成兩表L、R的共同接口交集及回寫後，在同一有序接口I上有：

\[
\pi_I(L)=\pi_I(R)=S.
\]

假設R未改變，L只刪列成L′。則T=π_I(L′)⊆S，新的共同支援恰為T。
若|T|=|S|，由有限集合包含關係得T=S，兩側都不必再刪列；若|T|<|S|，
仍須將R限制到T，保留所有相容的完整原列。**只比較數量之所以足夠，是先有T⊆S，
不是任意兩張同樣大小的表就能視為相等。**

如果兩側都變更，不能套用單側結論，仍完整求交集；三欄偶／奇parity負控制會得到空表，
即使每個一元／二元投影及兩邊列數都相同。若上次查詢未完成，沒有支援數可以重用。

底層 `SharedInterfaceIndex(monotone_updates=True)` 的使用契約是：
同一因子身份只可刪列，改列時增加revision；成長或替換使用新的身份。
`mark_seen(..., support_count=...)`須在兩側完整結果提交後記錄正確的共同支援數；
省略數量則不啟用這項捷徑。主引擎四個更新入口都只做域篩選或完整支援交集，
新增限制另建因子，符合此契約。一般未聲明單調的索引仍保留原演算法。

新增／退休因子會更新身份與相依索引，舊因子的支援數不能套到新因子。
所有查詢仍在完整結束後才提交因子列；中斷可保留已完成的加速索引，但不能提交部分交集。
佇列已取出但未完成的工作保持待處理，重試不能漏掉。

原圖、固定色、字面色框、完整fibres與倒序共同回填不變。
這是[有限圖完整消元契約](four_color_completeness.md)下的實作優化，
沒有新四色定理證明、Python形式化驗證或一般速度保證。

## 比較契約與證據

沿用固定40份原圖與固定色，每例工作5,000,000、完整表列1,000,000，
prefix枚舉、共同接口索引、原環與共同條件傳播。scan/delta除傳播模式外設定相同。
完整事件不可截斷，兩模式不可超限，才宣稱完整執行相等。

比較器逐份要求：**除傳播模式、實際工作計數與加速快取計數外，整份輸出相等**。
包括原圖、域、每一步全部輸入表及fibres、空列語義、原邊來源、事件敘述、
消元次序、回填色與最後判定。差異白名單寫在 `comparison.json`；不是只比SAT／UNSAT。

此外沿用獨立原圖驗證：4例枚舉全部原邊解，24例核對精確全域投影，
10例只核指定獨立見證、2例使用獨立無解參考。後12例不擴大成全部解核對。

初試只含佇列與單側支援重用：總檢查10,433,208→10,328,622，但時間12.61→13.05秒，
尚未加速。它促成本輪繼續檢查全圖mask重建與整表投影；
初試證據保留在[initial比較](../../../artifacts/four_color_propagation/initial/comparison.json)，
不覆寫成最終數字。改動前來源另存 `artifacts/four_color_propagation/baseline-source/scripts/`。

## 最終結果

[原排程完整比較](../../../artifacts/four_color_propagation/final/comparison.json) ·
[資訊分區併用比較](../../../artifacts/four_color_propagation/information/comparison.json)

| 固定40例設定 | 總檢查 | 接口交集檢查 | 求解秒數 |
| --- | ---: | ---: | ---: |
| 原排程＋scan | 10,433,208 | 4,050,067 | 12.86 |
| 原排程＋delta | 10,265,841 | 3,882,700 | 11.71 |
| information分區＋scan | 10,390,284 | 4,056,003 | 13.35 |
| information分區＋delta | 10,229,773 | 3,895,492 | 12.09 |

原排程下總檢查少1.60%、接口工作少4.13%、單次實測時間少8.92%。
資訊分區下分別少1.54%、3.96%、9.43%。各自都是37例少檢查、3例持平，無檢查增加例。
每種設定均27份合法著色、13份精確無解、0份超限；所有同排程的完整語義紀錄逐份相等。

原排程的累計表列149,040、完整證書列368,764、消元1,576次與候選檢查663,483均不變；
資訊分區下對應151,632／372,651／1,576／657,380，也逐項不變。
因此省下的不是刪掉更多解、減少表格證書或提前選色，而是重複的傳播與準備工作。

原排程中有18,980次單側支援重用、23,484次整表接口引用。
佇列實際處理110,000個待查配對，推入110,228次；舊掃描另訪問1,665,941個已完成配對。
額外相依索引仍有管理成本，沒有將它說成零工作。域簽章、佇列與快照準備
屬既有 `checks`之外的排程工作，計時包含它們，所以時間降幅大於關係檢查降幅。

每組均依序執行scan、delta，當時未同時跑測試。這是本機單次觀察，不是多次統計測速；
原排程有12例、資訊分區有13例牆鐘時間略增，即使檢查數沒增加。
原排程程序於求解後的最高RSS約259.5→261.7 MiB，為整個程序生命週期高水位，
不是單次求解淨配置，也不是節省RAM的證據。

本輪保留可選 `delta` 與原預設 `scan`。一般加速保證、全事件驅動的域／環傳播、
分區的全域最優選擇仍未建立；但在這批固定案例已得到保持完整輸出的傳播成本改善。

## 使用與重播

```bash
python3 scripts/four_color_lab.py solve graph.json --engine constraints \
  --intersections --interface-cache --propagation-method delta \
  --bucket-method prefix --json result.json

uv run --with-requirements requirements.txt python scripts/four_color_propagation_experiment.py \
  --out-dir /tmp/four-color-delta-replay --partition none

python3 -m unittest discover -s tools/tests -p 'test_four_color_delta_propagation.py' -v
```

API：`solve_constraints(graph, use_intersections=True, use_interface_cache=True,
propagation_method="delta")`。沒有可選RAM分組快取時也保持正確；容量不足就用完整臨時投影。
新比較目錄必須尚未存在。單次牆鐘量測包含佇列管理與傳播規劃，不代表一般加速倍數。

本輪僅更新本報告、四色導覽、約束引擎與相關優化報告入口、STATUS。
原消元完備性前提未改，HANDOFF、4CT與D停止點維持原義務。
